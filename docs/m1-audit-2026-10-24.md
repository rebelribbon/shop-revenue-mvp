## Findings fixed in this audit

1. **Cross-tenant reference in `audit_event` (isolation defect).** `audit_event.support_session_id` referenced `support_session(id)` alone. Direct SQL as `app_user`, in tenant A's context, inserted an A audit row pointing at B's support session. This was possible both as a user actor and as a support actor.
   - Fixed by migration `0008_audit_support_session_tenant_fk`: it adds `support_session(business_id, id)` and the composite FK.
   - `scripts/db/check-rls.ts` now fails CI on any tenant-to-tenant FK that omits `business_id`. It flagged this exact FK on the pre-0008 schema.
   - New tests cover the CI rule, the audit reference and the business-logo reference. The logo reference was already composite but had no test.
   - **0008 must still be applied to both hosted projects by the Deploy workflow.**
2. **PITR gate could never pass.** `deploy.yml` read `physical_backup_data.latest_physical_backup_unix_timestamp`. The Management API returns `latest_physical_backup_date_unix`. With PITR on, the old expression evaluated `0 > 0` and refused every production migration.
   - Fixed. The gate now requires `pitr_enabled == true` and a restore point no older than 24 hours.
   - It fails closed on any API error.
   - The token needs the fine-grained `backups_read` permission. That matches what was configured.
3. **Staging smoke could not read a protected Preview.** Plain `curl` got a 302 to the Vercel login page and `jq` failed on HTML. The smoke step also checked the branch alias, not the deployment the job had just created.
   - Fixed. `scripts/ci/hosted-smoke.sh` calls `vercel curl --deployment <url from vercel deploy>`, which sends the project's Protection Bypass for Automation secret using `VERCEL_TOKEN`.
   - Deployment Protection stays on.
   - The check also requires `/api/health` `version` to equal the commit being deployed.
   - Production uses the same script against its exact deployment, then checks that the public canonical domain serves the new commit.
   - If the project has no automation bypass secret, the first run creates one. It is listed under Project Settings → Deployment Protection.

## Credentials to rotate (values intentionally omitted)

Each item must be rotated and its dependent secret updated in the same sitting. Then the old value must be shown to fail and the new one to work.

| Credential | Dependents to update atomically | Verified rotated? |
| --- | --- | --- |
| Dev `app_user` password | Vercel **Preview** `DATABASE_URL_APP`; any local `.env.dev-hosted` | **No** — still listed as outstanding in the 2026-10-23 status. |
| Dev `migration_owner` password | GitHub env **staging** `DATABASE_URL_MIGRATION`; local env files | **No evidence.** |
| Prod `migration_owner` password | GitHub env **production** `DATABASE_URL_MIGRATION`; local env files | **No evidence.** |
| Dev `postgres` password, plus the four dev role passwords exposed on 2026-10-23 | Bootstrap tooling only | Recorded as rotated and verified (`28P01` on the old password) in `m1-report.md`. Not re-verified here. |
| Any prod role password typed into a chat or terminal during setup (`app_user`, `worker_user`, `admin_user`, prod `postgres`) | Vercel **Production** `DATABASE_URL_APP` (for `app_user`) | **Unknown.** Rotate if there is any doubt. |

Safe rotation order per credential:

1. Generate the value locally, for example `openssl rand -hex 24`.
2. `ALTER ROLE … PASSWORD …` in the Supabase SQL editor, so the value is never written to a shell history that is echoed.
3. Immediately update the dependent secret.
4. For Vercel, redeploy so the running functions pick it up.
5. Prove both directions: the new value connects, the old value is rejected.

Rotate `app_user` for production only in a quiet window, because live functions hold pooled connections.

Do not rotate `migration_owner` while a Deploy run is in progress.

## Other observations (not blocking M1)

- Production currently runs unmerged PR-branch code. That is acceptable for a pre-launch environment, but Deploy should be run from `main` after merge so production always matches the default branch.
- `deploy.yml` is `workflow_dispatch` only. Section 24 implies deploy on merge. Manual dispatch with production approval is a reasonable design-partner choice; record it if it is permanent.
- Tenant context is set with `set_config(..., true)` and is not bound to the transaction ID. A later `set_config` in the same transaction can still change the actor or tenant. Only server code issues SQL, so this is hardening, not a defect.
- E2E needed reruns on `d0f4036` (phone-viewport timing). It was green on the first attempt at `d5c3652`. Watch for recurrence.
- Supabase built-in SMTP is rate-limited. Custom SMTP is required before commercial use, as already recorded.
